# OpenMV 装甲板识别中的独立跟踪、运动预测与运动数据说明

## 1. 项目背景

当前系统使用 **OpenMV Pro Plus** 对装甲板进行视觉识别。

原始识别流程主要包括：
```
摄像头采集图像
    ↓
LAB 颜色阈值分割
    ↓
find_blobs() 提取红 / 蓝候选灯条
    ↓
灯条形状粗筛
    ↓
两两组合进行装甲板几何评分
    ↓
选出 geometry_score 最高的 pair
    ↓
计算装甲板中心 cx / cy
    ↓
输出目标位置
```

原程序已经具备以下主要功能：
- 红色 / 蓝色 LAB 阈值分割
- Blob 灯条候选筛选
- 灯条角度、长度、间距、错位等几何约束
- 红蓝装甲分别配对
- 从所有候选 pair 中选出几何评分最高的装甲板
- 计算最终装甲中心 `(cx, cy)`

但是在实际场景中存在明显误识别，例如：
- 窗户边缘被识别成灯条
- 天花板吊灯被识别成灯条
- 反光区域形成两个相似的长条 Blob
- 某一帧错误候选的几何评分突然超过真实装甲板
- 最终中心点瞬间跳到错误位置

因此，在单帧装甲识别之后，需要增加一个独立的**连续帧目标跟踪层**。

# 2. 为什么不能只依赖单帧识别

原始程序中的最终逻辑近似为：
当前帧找到 best_pair → 计算 cx / cy → 立即认为这是目标位置

这种逻辑存在一个问题：任何单帧误识别都会立刻影响最终输出。
例如真实装甲板中心连续为：
Frame 1 : (150, 120)
Frame 2 : (154, 119)
Frame 3 : (158, 118)

但 Frame 4 某个窗户突然获得更高的几何评分：Frame 4 : (270, 50)
如果没有时间维度上的判断，系统会直接认为：目标从 (158,118)突然移动到 (270,50)
对于无人机、云台或者移动机器人，这种错误输出可能直接造成控制系统突然大幅动作。

因此需要引入：
单帧检测 → 连续帧验证 → 运动预测 → 稳定目标

# 3. 独立跟踪模块的设计

为避免主程序中混入大量状态变量，连续帧跟踪被拆分成独立模块：
visual_color.py负责图像识别、灯条检测、装甲配对
armor_tracker.py负责连续帧确认、运动预测、跳点抑制

主程序只负责提供：found/color/cx/cy/target_size/now_ms

跟踪器返回：valid/stable_color/stable_cx/stable_cy

整体结构：
OpenMV 图像 → 灯条检测 → 装甲板配对 → 得到原始 cx / cy / w / h → MotionTracker.update(...) → 得到稳定后的 stable_cx / stable_cy → 显示 / UART发送 / 飞控使用

# 5. MotionTracker 的输入数据

## 5.1 found
表示当前帧是否找到了一个合法的装甲候选。
found = True意味着当前存在 `best_pair`。
found = False意味着当前帧没有找到合法装甲。

## 5.2 color
当前候选装甲板的颜色："RED"/"BLUE"
跟踪器可以利用颜色避免红蓝目标之间突然切换。

## 5.3 cx / cy
当前帧通过装甲板配对得到的原始中心位置：(cx,cy)  单位：pixel
例如 QVGA：图像尺寸 = 320 × 240
图像中心约为：(160, 120)
因此：cx = 200,cy = 100 表示目标位于图像中心右侧、上方。

## 5.4 target_size
当前装甲板在图像中的代表尺寸。
当前实现推荐：target_size = max(w, h)
其中：w = 两根灯条组成的整体装甲候选宽度；h = 两根灯条组成的整体装甲候选高度

使用目标尺寸的原因是：同样的物理运动，对于近距离的大目标，可能产生更明显的像素变化.因此动态跟踪门限应该考虑目标当前在画面中的尺寸。

## 5.5 now_ms
当前时间：now_ms = time.ticks_ms()
用于计算两帧之间真实经过的时间：dt = time.ticks_diff(now_ms, old_ms)
相比直接使用：pixel/frame,使用：pixel/ms更合理。
因为 OpenMV 的 FPS 并不一定完全稳定。

# 6. 像平面速度是什么
跟踪器内部的：stable_vx,stable_vy表示的是：**装甲板中心在图像平面中的运动速度。** 单位：pixel / ms,或者换算为：pixel / s
例如：
上一帧：
cx = 120
cy = 100

当前帧：
cx = 140
cy = 104

dt = 20 ms
那么：
vx = (140 - 120) / 20
   = 1 pixel/ms

vy = (104 - 100) / 20
   = 0.2 pixel/ms
也可以写成：
vx = 1000 pixel/s
vy = 200 pixel/s

这个速度只描述：目标在当前摄像头画面中如何移动。

# 7. 像平面速度不是无人机速度

这一点非常重要。像平面速度≠无人机物理速度
无人机物理速度通常为：m/s
例如：Vx = 2 m/s,Vy = 1 m/s,Vz = 0.2 m/s
而图像速度为：pixel/s,两者不能直接等价。

像平面中的目标运动可能由以下因素共同造成：目标自身运动+无人机平移+无人机姿态旋转+相机旋转+目标距离变化+透视投影
因此跟踪器中的：stable_vx,stable_vy不应该理解成无人机速度,也不应该理解成：装甲板真实世界中的运动速度
它仅仅是：image velocity——像平面速度

# 8. 为什么可以使用像平面速度进行防误识别
防止目标突然跳到窗户时，并不需要知道真实三维速度。
例如历史已经确认：
Frame 1 : x = 100
Frame 2 : x = 120
Frame 3 : x = 140
说明目标最近大约在：+20 pixel/frame 向右移动。
那么下一帧可以预测：x_pred ≈ 160，如果当前检测：x_measure = 164就非常合理。
但如果突然得到：x_measure = 280，那么：误差 = 120 pixel，这个点非常可疑，因此可以先拒绝它接管稳定目标。
这并不要求知道：无人机速度是多少，装甲板真实速度是多少，目标距离是多少
只需要判断：当前目标在画面中的运动是否连续。

# 9. 为什么这不是“自己算速度，再用速度证明自己”

这里容易出现一个逻辑疑问：既然速度也是从图像算出来的，再用这个速度判断图像是否正确，是不是循环论证？如果算法设计错误，确实可能出现这种问题。

错误做法：当前点突然从 100 跳到 250 → 立即计算速度 = +150 → 因为速度很大 → 扩大允许门限 → 于是认为 250 是合理的
这属于错误的自我强化。

正确做法必须严格按照：历史已确认状态 → 得到旧速度 → 先预测当前帧 → 拿当前测量和预测比较 → 通过验证 → 当前点才允许参与速度更新
即：
旧位置 + 旧速度 → 预测位置 → 与当前测量比较 → 可信？
                                        ┌────┴────┐
                                        是        否
                                        ↓         ↓
                                     更新速度   pending
所以：当前帧的错误位置不能先修改速度，再利用修改后的速度证明自己合理。

# 10. Alpha-Beta 运动预测
跟踪模块采用的是轻量级的 Alpha-Beta Filter 思路。
首先：上一帧稳定位置：P_old；上一帧稳定速度：V_old
经过：dt
预测：P_pred = P_old + V_old × dt

例如：
P_old = 150
V_old = 0.75 pixel/ms
dt = 20 ms
得到：
P_pred = 165
当前视觉测量：
P_measure = 168
预测误差：
error = 168 - 165 = 3 pixel
误差较小，因此可以认为当前识别和历史运动模型一致。

位置更新：P_new = P_pred + alpha × error
速度更新：V_new = V_old + beta × error / dt
其中：alpha控制位置有多相信当前视觉测量；beta控制速度对加速 / 减速有多敏感。

# 11. stable 和 pending 两套状态
独立跟踪模块使用了两套目标状态。
## 11.1 stable 表示：已经通过连续帧验证，当前正式认可的目标。
保存：
stable_color
stable_cx
stable_cy
stable_vx
stable_vy
stable_size
stable_time
只有 stable 目标才应该：
- 画最终绿色中心
- 发送给 UART
- 给飞控作为控制目标

## 11.2 pending 表示：突然出现，但是还没有证明自己可靠的新候选。

例如 stable 当前在：(160,120)，预测下一帧大约：(175,120)
但当前单帧突然识别：(40,50)，不会马上：stable = (40,50)
而是：pending = (40,50)，pending_count = 1
如果下一帧又出现：(42,51)，则：pending_count = 2
如果第三帧：(45,51)，满足连续运动：ending_count = 3
这时才能正式把新位置升级为 stable。

# 12. 为什么无人机运动时 pending 不能要求位置几乎不变
因为无人机本身可能运动。
例如：
Frame 1 : (100, 120)
Frame 2 : (132, 118)
Frame 3 : (165, 116)
这是一个持续运动的真实目标。
如果要求连续 3 帧中心几乎相同会导致无法锁定。
因此 pending 自己也会估计：pending_vx，pending_vy，从第二帧开始估算图像速度。
第三帧开始根据：pending_cx + pending_vx × dt预测候选位置。
因此所谓“连续三帧确认”并不是三帧坐标完全一样，而是三帧在空间和运动趋势上属于同一个连续目标。

# 13. 动态 Gate
跟踪器不是使用固定：MAX_CENTER_JUMP，而是动态计算一个允许误差范围：gate
稳定跟踪阶段大致形式为：gate =基础容错+目标尺寸影响+当前运动速度影响
即：gate = (TRACK_BASE_GATE + TRACK_SIZE_FACTOR * size_ref + TRACK_SPEED_FACTOR * expected_move)
其中：TRACK_BASE_GATE表示基本容错；TRACK_SIZE_FACTOR × size_ref表示目标越大，允许一定程度上更大的像素运动；TRACK_SPEED_FACTOR × expected_move表示历史运动越快，下一帧允许的运动范围也应该相应增大；TRACK_MAX_GATE限制 Gate 最大值，防止系统无限扩大搜索范围。

# 14. 丢失目标时如何处理
如果某一帧完全没有检测到 `best_pair`：found = False
如果之前没有 stable：直接保持无目标；如果已经存在 stable：lost_count += 1，只要：lost_count <= MAX_LOST_FRAMES 就不会立刻输出：COLOR=NONE
而是继续根据旧速度短时间预测：
stable_cx += stable_vx × dt
stable_cy += stable_vy × dt
同时：stable_vx，stable_vy逐渐衰减。
作用是避免：某一帧曝光变化，某一帧灯条断裂，某一帧被遮挡等导致目标立即消失。
如果连续丢失超过：MAX_LOST_FRAMES 才正式认为目标消失。

# 15. MotionTracker 主要参数解释
## CONFIRM_FRAMES
*confirm_frames = 3
含义：一个新目标需要连续多少帧运动一致才能正式锁定。
较小：响应快,容易误锁
较大：稳定,重新锁定延迟增加

## MAX_LOST_FRAMES
*max_lost_frames = 4
含义：已稳定目标最多允许多少帧没有正常匹配。
值越大：抗短暂遮挡能力更强,但也会在目标已经真正消失后继续预测更久

## ACQUIRE_BASE_GATE
初次捕获新目标时的基本门限。
因为刚发现目标时还没有可靠速度，所以应该比稳定跟踪阶段宽松。

## ACQUIRE_SIZE_FACTOR
根据新候选尺寸增加允许范围。

## ACQUIRE_SPEED_FACTOR
pending 已经估计出速度以后，根据预计移动距离增加搜索范围。

## ACQUIRE_MAX_GATE
新候选确认阶段允许的最大像素误差。

## TRACK_BASE_GATE
稳定跟踪阶段最基本的像素误差容忍。

## TRACK_SIZE_FACTOR
根据装甲在画面中的尺寸扩大稳定跟踪门限。

## TRACK_SPEED_FACTOR
根据历史速度扩大跟踪门限，无人机快速运动时这一项非常重要。

## TRACK_MAX_GATE
稳定跟踪最大允许范围。
用于防止：速度估计异常
→ gate越来越大
→ 错误候选越来越容易进入

## TRACK_ALPHA
位置更新系数。
较大：更相信当前视觉测量，响应更快，抖动可能更明显
较小：轨迹更平滑，响应变慢

## TRACK_BETA
速度更新系数。
较大：加速 / 减速响应快，速度容易受噪声影响
较小：速度稳定，对快速机动响应慢

## LOST_VELOCITY_DECAY
丢失目标以后速度衰减。
例如：lost_velocity_decay = 0.92
每丢失一帧：V_new = V_old × 0.92避免目标短暂丢失后预测坐标一直无限运动。

# 16. 三种不同的“速度”
视觉系统中必须区分三个概念。
## 16.1 像平面速度
单位：pixel/s pixel/ms
来源：目标连续帧图像坐标变化
例如：u_dot，v_dot
它表示：目标相对于当前相机画面的运动速度。
当前 `MotionTracker` 使用的就是这一类速度。

## 16.2 无人机物理速度
单位：m/s
表示无人机在三维真实空间中的平移速度：Vx Vy Vz
来源可能是：飞控状态估计/GPS/光流/VIO/IMU + 状态估计器
它不能直接等于像素速度。

## 16.3 相机角速度
单位：rad/s deg/s
表示相机绕自身三个轴旋转的速度：ωx/ωy/ωz
如果摄像头刚性固定在无人机上：相机角速度≈经过坐标变换后的机体陀螺仪角速度
通常来源于：飞控 IMU gyroscope

# 17. 三种速度之间的物理关系
目标在图像中的运动，大致由：目标运动+相机平移+相机旋转 共同决定。
因此：像平面速度可以看成所有三维相对运动经过相机投影之后的结果。

# 18. 无人机平移速度为什么不能直接转换成像素速度
假设无人机横向运动：Vx = 1 m/s
如果目标距离：Z = 2 m ,图像中的运动会很大。
如果目标距离：Z = 20 m ,同样Vx = 1 m/s图像运动会明显更小。
平移产生的图像运动通常和：V / Z有关。
因此想把：无人机 m/s转换成：pixel/s至少还需要：目标深度Z以及相机参数。

# 19. 相机旋转为什么特殊
对于纯旋转：无人机原地 Yaw即使真实目标完全静止，目标仍会在画面中移动
而且纯旋转造成的角运动基本不依赖目标距离 Z
因此，在无人机装甲识别中：飞控 IMU 的角速度通常比无人机 GPS 线速度更适合用于视觉运动补偿。

# 20. 相机内参矩阵 K
相机标定通常得到：

\[
K =
\begin{bmatrix}
f_x & 0 & c_x\\
0 & f_y & c_y\\
0 & 0 & 1
\end{bmatrix}
\]

其中：
fx水平焦距，单位 pixel。
fy垂直焦距，单位 pixel。
cx，cy相机主点 / 光心在图像中的位置。

对于：320 × 240，主点可能接近：(160,120)，但正式角度计算时不能默认一定正好在图像中心。

# 21. 像素坐标转换成视线角度

已知像素位置：
u
v

相机内参：
fx
fy
cx
cy

可以计算归一化坐标：
\[
x = \frac{u-c_x}{f_x}
\]

\[
y = \frac{v-c_y}{f_y}
\]

水平方向视线角可近似写成：
\[
\theta_x =
\arctan
\left(
\frac{u-c_x}{f_x}
\right)
\]

垂直方向类似：
\[
\theta_y =
\arctan
\left(
\frac{v-c_y}{f_y}
\right)
\]

因此：像素位置可以通过相机内参转换为目标相对相机光轴的角度


# 22. 像平面速度转换成视线角速度

连续两帧得到：
θ(n-1)
θ(n)

那么：
\[
\dot{\theta}
\approx
\frac{
\theta_n-\theta_{n-1}
}{
\Delta t
}
\]

单位：rad/s，这叫：LOS angular rate——视线角速度
需要注意：视线角速度≠相机自身角速度

前者描述：目标方向相对于相机变化多快；后者描述：相机本身旋转多快。

# 23. 图像运动的完整关系
令归一化图像坐标：
\[
x=\frac{u-c_x}{f_x}
\]

\[
y=\frac{v-c_y}{f_y}
\]

相机平移速度：
\[
T_x,T_y,T_z
\]

相机角速度：
\[
\omega_x,\omega_y,\omega_z
\]

目标深度：
\[
Z
\]

则经典图像运动模型的一种形式为：
\[
\dot x =
-\frac{T_x}{Z}
+
x\frac{T_z}{Z}
+
xy\omega_x
-
(1+x^2)\omega_y
+
y\omega_z
\]

\[
\dot y =
-\frac{T_y}{Z}
+
y\frac{T_z}{Z}
+
(1+y^2)\omega_x
-
xy\omega_y
-
x\omega_z
\]

不同相机坐标系约定下，符号可能不同，但结构一致。
其中可以看到：
## 平移项
包含：
\[
\frac{T_x}{Z},
\frac{T_y}{Z},
\frac{T_z}{Z}
\]
因此：相机平移造成多少图像运动与目标深度有关。
## 旋转项
包含：
\[
\omega_x,
\omega_y,
\omega_z
\]
没有深度：
\[
Z
\]
因此：相机旋转引起的图像运动与目标距离没有同样强的深度依赖。
最后通过：
\[
\dot u = f_x\dot x
\]

\[
\dot v = f_y\dot y
\]
得到像素速度。

# 24. 哪些操作需要进行相机标定

## 不需要相机标定

如果只做：连续帧防跳/目标轨迹平滑/像素速度估计/像素位置运动预测
那么不需要相机内参 K
当前独立的：armor_tracker.py属于这一层。
它只需要：cx，cy，dt，target_size，color

## 需要相机标定
如果想进行：像素位置 → 真实视线角度
需要：fx，fy，cx，cy即相机内参。
如果想进行像素速度 → LOS视线角速度，同样需要相机内参 + dt
如果想进行IMU相机角速度 → 预测像素移动
也需要：相机内参

# 25. 如果融合飞控 IMU，还需要相机外参
飞控 IMU 测量的是：机体坐标系中的角速度。

但是视觉模型使用的是：相机坐标系中的角速度。
如果相机和飞控不是完全同轴，需要：
\[
\omega_{camera}
=
R_{camera \leftarrow body}
\omega_{body}
\]

其中：R_camera<-body是机体坐标系到相机坐标系的旋转矩阵。
这个矩阵属于：相机-机体外参，所以完整的 IMU + 视觉融合最终可能需要：相机内参 K+镜头畸变参数+相机和机体之间的外参 R+飞控 IMU 角速度

# 26. 如果还想融合无人机线速度
如果希望使用：飞控的 Vx / Vy / Vz直接预测目标在画面中的运动，则还需要：目标距离 Z

可能的距离来源包括：
- 装甲板已知尺寸 + PnP
- 双目
- ToF
- 激光测距
- 深度相机
- 其他状态估计

因此：线速度 → 像素运动 比：角速度 → 像素运动 需要更多信息。
